《构建之法》阅读问题与讨论

讨论草稿 · 2026-09-05

本文围绕 AI 编程智能体（coding agent）对软件工程方法的影响整理问题。第一、二章的问题由阅读讨论形成，其中人工审查的可执行性来自本人提出的疑问，其余为 AI 辅助扩展的候选问题，尚待本人筛选并补充个人判断。

讨论依据为作者仓库第一、二章的配套概述与问答，未据此声称读完纸质教材全文。

第一章：概论

1. AI 只能理解局部语法、全局理解必须在人脑中完成，这个分工是否已经过时？

出处：作者配套问答 1.7，建议运行系统、抓业务主干，再用 AI 解释局部代码，并将全局业务理解保留给人。

疑问：这一界限接近代码片段助手的能力边界。现在 agent 可以检索整个仓库、追踪调用和数据流、执行程序并根据结果修改理解。Anthropic 的多 agent 编译器实验展示了跨模块开发及专门承担优化、设计检查的 agent，但也报告了能力上限和反复回归。因此，不能据此证明 agent 完全理解系统；同样也不能预先把其能力限定为局部语法。

追问：应如何比较人和 agent 对全局业务的理解？能否通过预测需求变更影响、定位跨模块故障、解释状态迁移等任务检验，而不以“是否在人脑中”作为标准？人需要持有的最低系统知识是什么？

可验证方向：对同一仓库设置未见过的跨模块变更，比较人工、agent 和人机协作对影响范围的预测及实际漏项。

2. “没有银弹”是否被用来提前否定 agent 对整个工程流程的改变？

出处：1.2 的固有难题与配套问答 1.3、1.10。

疑问：需求复杂性仍然存在，并不能推出解决它的成本没有显著下降。agent 可能同时改变调查、实现、测试和协作成本。StrongDM 描述以规格、外部场景和服务模拟驱动 agent 持续开发的实践，其真实性能仍需独立验证，但它已经超出局部代码生成。

追问：“复杂性没有消失”与“处理复杂性的成本下降”是否被混为一谈？应以哪些端到端指标判断技术突破：交付周期、缺陷、人工时间，还是后续变更成本？哪些证据能够推翻“AI 只提高局部效率”的判断？

3. AI 写出的普通软件与运行时包含 AI 的软件，是否应该分开讨论？

出处：配套问答 1.3 将 AI 时代的复杂性与模型黑盒、提示词变化、幻觉和不可复现联系起来。

疑问：由 agent 编写的确定性日期转换程序，在运行时未必调用模型。开发工具的不确定性与产品运行时的不确定性是不同问题。如果把二者混在一起，就可能把模型幻觉、提示词敏感等风险泛化到全部 AI 生成软件。

追问：对于 AI 生成的传统程序，与包含自主 agent 的产品，质量保证应分别覆盖哪些层次？哪些风险来自开发过程，哪些来自部署后的系统行为？

4. “足够好”的标准，是否应随生成与验证成本改变？

出处：1.3 与配套问答 1.4，强调有限资源下的质量权衡。

疑问：权衡原则仍然成立，但某类测试、修复和原型的成本下降后，过去合理的缺陷容忍水平未必仍然合理。另一方面，生成提速也可能使待验证代码积压，拉高验证成本。

追问：agent 带来的效率收益应如何分配给更快发布、更高质量及更大功能范围？什么证据表明某项质量要求已经从“不经济”变为值得执行？教材能否区分稳定的权衡原则与会变化的成本假设？

5. 可维护性的核心资产，是否从代码扩展到了规格、验收场景和生成环境？

出处：配套问答 1.2 已承认可维护性需要清晰模块边界和测试，以支持 AI 局部重写。

疑问：这是配套材料已经更新的观点，需要继续推进。如果日常修改主要交给 agent，交接时还应保留哪些需求理由、验证场景、依赖信息和工具条件？仅留下整洁代码可能不足以复现生成和判断过程；同时也不应假定提示词可以代替代码和历史行为。

追问：给接手者同一份代码，分别提供或不提供需求决策及验收场景，其维护效果有何区别？维护性是否应同时衡量人和 agent 完成后续变更的成本？

第二章：个人技术和流程／PQ 工程素养

1. 人工审查能否继续作为普遍的质量保障前提？

出处：2.1、配套问答 2.2 与 PQ 关于 AI 测试审查和最终责任的题目。

本人的疑问：AI 生成代码的速度和规模不断增长，人工充分审查可能难以执行。我也看到一些社交媒体开发者表示不阅读 Vibe Coding 生成的代码。该观察不是开发者总体比例的统计；不阅读代码也不等于不验证软件。

现实对照：StrongDM 公开描述不进行人工代码审查的流程；Anthropic 的 agent 审查保留人工批准；Simon Willison 区分逐行读代码与验证实际改动。这些实践存在不同适用条件，尚不能据此宣布人工审查无用。

追问：承担责任需要何种验证证据？什么任务适合人工深读，什么任务可以依赖独立行为测试或 agent 审查？应比较漏检率与总验证成本，而不能把“人看过”自动视为可靠。

2. 同一 agent 可修改代码、测试和门禁时，TDD 的约束还独立吗？

出处：2.1 的 TDD、回归测试和 2.2 的质量门禁。

疑问：agent 能修改检查自身工作的标准。测试全绿可能来自正确实现，也可能来自弱化断言或改变测试。StrongDM 因此把部分场景置于实现仓库之外。

追问：哪些测试应由开发 agent 修改，哪些验收依据应独立保存？测试和实现由同一模型产生时，怎样避免共同的需求误解？课程是否需要把验收依据的独立性与修改权限纳入 TDD？

3. 为什么必须由人先定位性能热点，再指挥 AI 具体修改？

出处：配套问答 2.6 的人工性能分析后精准指挥 AI 的流程。

疑问：真实测量仍然必要，但 agent 已能运行工具并根据结果循环优化。人提前指定数据结构可能限制其探索。

追问：能否由人定义正确性、内存与时间约束，由 agent 自主寻找方案并交付测量证据？应在什么条件下选择逐步指导或目标委派？

4. 工程能力和估时，应评价个人还是人机组合？

出处：2.4 与配套问答 2.8，强调心智模型和交付预测。

疑问：实际产出受模型、工具、上下文与反馈环境影响。工具版本变化会改变同一人的交付能力。以历史人工经验估时，可能难以反映当前能力。

追问：课程怎样分别评价基础理解、验证能力与委派能力？是否应比较完整交付的人工时间、模型成本和缺陷，而非只评价个人预测是否准确？

5. 交付要求与学习要求是否应分开？

出处：2.4 的编程练习和工程成长。

疑问：不读全部代码的工作方式可能达到交付标准，但未必帮助初学者形成调试直觉。反之，教学中必要的手工练习，也未必是生产中最有效率的流程。

追问：哪些能力需要脱离 agent 独立掌握？哪些可以通过指挥、质疑和核验 agent 培养？应怎样检验学生对系统的理解，而不把手写代码量作为代理指标？
